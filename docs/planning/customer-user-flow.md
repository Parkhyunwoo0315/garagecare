# 1. Overview

## 1.1 Purpose

본 문서는 GarageCare 고객용 웹사이트의 주요 사용자 흐름(User Flow)과 이용 과정에서 발생할 수 있는 예외 상황을 정의한다.

고객이 정비소 정보를 탐색하고, 회원가입 및 로그인, 차량 등록, 정비 예약, 예약 조회 및 취소까지 일관된 경험으로 이용할 수 있도록 설계한다.

정상적인 이용 흐름뿐 아니라 사용자 입력 오류, 인증 만료, 데이터 충돌, 네트워크 장애 및 실제 정비소 운영 상황까지 고려한다.

## 1.2 Objectives

- 고객이 원하는 작업을 직관적으로 완료할 수 있도록 한다.
- 사용자의 실수를 가능한 한 사전에 방지한다.
- 오류 발생 시 원인과 해결 방법을 명확하게 안내한다.
- 중복 예약 및 데이터 불일치 가능성을 줄인다.
- 인증 및 인가 정책을 일관되게 유지한다.
- 장애 발생 시 고객의 입력 내용과 작업 상태를 가능한 한 보존한다.
- 고객과 정비소 모두에게 잘못된 예약 정보를 제공하지 않는다.
- 실제 운영 환경에서 발생하는 예외를 체계적으로 관리한다.

## 1.3 Scope

### In Scope

- 정비소 정보 탐색
- 회원가입 및 로그인
- 차량 등록 및 관리
- 정비 예약
- 예약 조회 및 취소
- 마이페이지
- 공지사항
- 공통 내비게이션
- 오류 및 예외 처리 UX

### Out of Scope

- 온라인 결제 및 환불
- AI 기반 정비 상담
- 차량 고장 예측
- 자동 정비 주기 추천
- 외부 정비소 연동
- 차량 정비 이력 자동 수집

# 2. User Flow Design Principles

## 2.1 Error Prevention First

오류 발생 이후의 안내보다 오류를 사전에 방지하는 설계를 우선한다.

예를 들어 예약할 수 없는 날짜는 선택 단계에서 구분하고, 차량 선택이 필요한 경우 등록 차량 목록을 제공한다.

단, 화면에서 입력을 제한하더라도 서버에서 반드시 동일한 조건을 검증한다.

## 2.2 Clear Feedback

사용자의 작업 결과를 명확하게 전달한다.

- 작업 성공
- 입력 오류
- 접근 권한 부족
- 처리 중
- 처리 실패
- 처리 결과 확인 필요

각 상태는 구분 가능한 메시지와 화면으로 제공한다.

## 2.3 Preserve User Context

로그인 만료나 입력 오류가 발생하더라도 가능한 한 사용자가 진행하던 작업으로 돌아올 수 있도록 설계한다.

민감한 정보는 보존하지 않으며, 데이터 보존 방식은 보안 요구사항을 고려하여 결정한다.

## 2.4 Safe Operations

예약 신청 및 취소와 같이 실제 운영에 영향을 미치는 작업은 중복 실행이나 의도하지 않은 상태 변경을 방지한다.

## 2.5 No False Confirmation

서버에서 예약 저장이 확인되기 전까지 예약이 완료되었다고 표시하지 않는다.

네트워크 오류 등으로 처리 결과가 불확실한 경우에도 성공이나 실패를 임의로 단정하지 않는다.

## 2.6 Accessible Recovery

오류 메시지는 색상에만 의존하지 않고 텍스트로 제공한다.

키보드와 모바일 터치 환경에서도 오류를 확인하고 복구할 수 있어야 한다.

# 3. User Types & States

## 3.1 User Types

| User Type | Description |
|---|---|
| Guest | 로그인하지 않은 방문자 |
| MEMBER | 일반 로그인 회원 |
| ADMIN | 관리자 권한 회원 |

ADMIN도 고객용 기능을 사용할 경우 본인 소유 차량 및 예약 데이터에만 접근한다.

## 3.2 Session States

| State | Description |
|---|---|
| Unauthenticated | 로그인하지 않은 상태 |
| Authenticated | 유효한 로그인 세션 |
| Session Expired | 로그인 세션이 만료된 상태 |
| Invalid Session | 세션 정보가 유효하지 않은 상태 |
| Authorization Denied | 인증되었으나 요청한 작업의 권한이 없는 상태 |

## 3.3 Reservation States

예약 상태는 기존 GarageCare 도메인 모델을 기준으로 확정한다.

사용자 화면에서는 내부 상태값을 그대로 노출하기보다 이해하기 쉬운 표현을 사용한다.

| Conceptual State | Customer Meaning |
|---|---|
| Requested | 예약 신청 접수 |
| Confirmed | 예약 확정 |
| Completed | 예약된 정비 업무 완료 |
| Cancelled | 예약 취소 |
| Rejected | 예약 신청 거절 |

※ 위 상태는 사용자 흐름을 설명하기 위한 개념적 분류이다. 실제 구현 시 기존 ReservationStatus와 매핑해야 하며, 존재하지 않는 상태를 임의로 추가하지 않는다.

# 4. Flow 01 — First-Time Visitor

## 4.1 Objective

신규 고객이 정비소 정보를 확인하고 예약을 시작할 수 있도록 한다.

## 4.2 Happy Path

```text
GarageCare 접속
        ↓
메인 페이지 표시
        ↓
정비소 및 서비스 정보 확인
        ↓
예약하기 선택
        ↓
로그인 또는 회원가입
        ↓
차량 등록
        ↓
정비 예약
        ↓
예약 결과 확인
```

## 4.3 Exception Scenarios

| ID | Exception | Expected Behavior |
|---|---|---|
| HOME-E01 | 정비 서비스 정보 없음 | 빈 화면 대신 안내 문구 표시 |
| HOME-E02 | 공지사항 없음 | 공지사항이 없다는 안내 표시 |
| HOME-E03 | 정비소 위치 정보 미등록 | 확인되지 않은 주소나 지도를 표시하지 않음 |
| HOME-E04 | 외부 지도 로딩 실패 | 텍스트 주소와 연락처 제공 |
| HOME-E05 | 서비스 데이터 조회 실패 | 다른 메뉴 이용 가능 상태 유지 |
| HOME-E06 | 예약하기 선택 시 비로그인 | 로그인 페이지로 이동 |
| HOME-E07 | 모바일 화면 레이아웃 오류 | 핵심 메뉴와 예약 CTA 접근성 유지 |
| HOME-E08 | 오래된 공지사항 노출 | 공지 작성일과 유효성 관리 필요 |

## 4.4 UX Requirements

- 정비소 기본 정보는 로그인 없이 확인할 수 있어야 한다.
- 정비소 연락처는 모바일에서 쉽게 사용할 수 있어야 한다.
- 예약 CTA는 주요 화면에서 쉽게 찾을 수 있어야 한다.
- 일부 콘텐츠 조회 실패가 홈페이지 전체 장애로 이어지지 않도록 설계한다.

# 5. Flow 02 — Registration & Authentication

## 5.1 Objective

고객이 회원가입과 로그인을 완료하고 원래 진행하던 작업으로 복귀할 수 있도록 한다.

## 5.2 Happy Path

```text
예약하기 선택
        ↓
로그인 필요
        ↓
로그인 페이지
        ↓
로그인 성공
        ↓
원래 요청한 화면 복귀
        ↓
예약 진행
```

## 5.3 Registration Exceptions

| ID | Exception | Expected Behavior |
|---|---|---|
| AUTH-E01 | 필수 입력값 누락 | 누락된 필드 안내 |
| AUTH-E02 | 잘못된 입력 형식 | 필드별 오류 메시지 표시 |
| AUTH-E03 | 중복 회원 정보 | 중복 여부 안내 |
| AUTH-E04 | 비밀번호 정책 미충족 | 요구 조건 안내 |
| AUTH-E05 | 비밀번호 확인 불일치 | 해당 입력 필드 안내 |
| AUTH-E06 | 회원가입 중 새로고침 | 민감정보를 제외한 입력 보존 여부 검토 |
| AUTH-E07 | 회원가입 버튼 중복 클릭 | 중복 제출 방지 |
| AUTH-E08 | 서버 오류 | 재시도 가능 여부 안내 |

## 5.4 Login Exceptions

| ID | Exception | Expected Behavior |
|---|---|---|
| AUTH-E09 | 로그인 정보 불일치 | 계정 존재 여부를 과도하게 노출하지 않는 오류 안내 |
| AUTH-E10 | 필수 입력값 누락 | 입력 요청 |
| AUTH-E11 | 로그인 중 네트워크 오류 | 처리 결과 확인 및 재시도 안내 |
| AUTH-E12 | 로그인 이후 세션 생성 실패 | 로그인 완료로 표시하지 않음 |
| AUTH-E13 | 잘못된 redirectURL | 안전한 기본 페이지로 이동 |
| AUTH-E14 | 외부 사이트로 리다이렉트 시도 | 외부 리다이렉트 차단 |
| AUTH-E15 | 이미 로그인한 사용자의 로그인 페이지 접근 | 적절한 기본 화면으로 안내 |
| AUTH-E16 | 세션 만료 | 재로그인 안내 |
| AUTH-E17 | 로그아웃 이후 뒤로 가기 | 보호된 정보 재노출 방지 |

## 5.5 Session Expiration Flow

```text
로그인 상태
    ↓
보호된 작업 진행
    ↓
세션 만료
    ↓
작업 요청
    ↓
인증 필요 응답
    ↓
로그인 안내
    ↓
재로그인
    ↓
안전한 화면으로 복귀
```

### Design Requirements

- 세션 만료 시 로그인 화면으로 이동한다.
- 로그인 이후 원래 요청한 안전한 경로로 복귀할 수 있도록 한다.
- 비밀번호 등 민감정보는 임시 저장하지 않는다.
- 세션 만료 직전의 변경 요청을 자동으로 재전송하지 않는다.
- 변경 작업은 재인증 이후 사용자가 다시 확인하도록 한다.

# 6. Flow 03 — Vehicle Registration

## 6.1 Objective

고객이 차량을 등록하고 이후 예약 과정에서 해당 정보를 재사용할 수 있도록 한다.

## 6.2 Happy Path

```text
마이페이지
    ↓
내 차량
    ↓
차량 등록
    ↓
차량 정보 입력
    ↓
입력값 검증
    ↓
차량 저장
    ↓
등록 완료
    ↓
차량 목록
```

## 6.3 Exception Scenarios

| ID | Exception | Expected Behavior |
|---|---|---|
| VEH-E01 | 필수 차량 정보 누락 | 필수 항목 안내 |
| VEH-E02 | 생산연도 형식 오류 | 올바른 입력 형식 안내 |
| VEH-E03 | 미래 생산연도 입력 | 실제 허용 정책에 따라 검증 |
| VEH-E04 | 차량명 또는 모델명 길이 초과 | 입력 길이 제한 안내 |
| VEH-E05 | 특수문자 포함 | 허용 가능한 문자 정책 적용 |
| VEH-E06 | 동일 차량 중복 등록 | 중복 가능성 안내 및 정책에 따라 처리 |
| VEH-E07 | 차량 등록 중 세션 만료 | 재로그인 후 재입력 안내 |
| VEH-E08 | 차량 저장 중 서버 오류 | 저장 여부 확인 후 재시도 |
| VEH-E09 | 차량 등록 버튼 중복 클릭 | 중복 요청 방지 |
| VEH-E10 | 등록된 차량 없음 | 차량 등록을 유도하는 Empty State 표시 |
| VEH-E11 | 다른 회원의 차량 조회 | 접근 차단 |
| VEH-E12 | 존재하지 않는 차량 ID | 적절한 오류 페이지 제공 |
| VEH-E13 | 예약에 사용된 차량 수정 | 기존 예약과의 데이터 정합성 검토 |
| VEH-E14 | 예약에 사용된 차량 삭제 | 삭제 가능 조건 및 참조 무결성 검토 |

## 6.4 Vehicle Data Integrity

차량 정보는 예약 데이터와 연결되므로 변경 및 삭제 정책을 신중하게 설계한다.

### Recommended Policy

- 차량 수정 시 본인 소유 여부를 검증한다.
- 차량 삭제 시 연결된 예약의 존재 여부를 확인한다.
- 예약과 연결된 차량을 무조건 삭제하지 않는다.
- 기존 예약 내역의 차량 정보가 손상되지 않도록 한다.
- 필요하다면 물리 삭제 대신 비활성화 정책을 검토한다.

※ 실제 차량 삭제 정책은 기존 도메인 구조와 데이터 관계를 확인한 후 확정한다.

# 7. Flow 04 — Reservation Creation

## 7.1 Objective

고객이 차량과 정비 서비스를 선택하여 예약을 안전하게 신청할 수 있도록 한다.

## 7.2 Happy Path

```text
예약하기
    ↓
로그인 상태 확인
    ↓
등록 차량 확인
    ↓
차량 선택
    ↓
정비 서비스 선택
    ↓
예약 날짜 및 시간 선택
    ↓
예약 정보 확인
    ↓
예약 신청
    ↓
서버 검증
    ↓
예약 저장
    ↓
예약 결과 표시
```

## 7.3 Input Exceptions

| ID | Exception | Expected Behavior |
|---|---|---|
| RES-E01 | 등록된 차량 없음 | 차량 등록 화면 안내 |
| RES-E02 | 차량 미선택 | 차량 선택 요청 |
| RES-E03 | 정비 서비스 미선택 | 서비스 선택 요청 |
| RES-E04 | 날짜 미선택 | 날짜 선택 요청 |
| RES-E05 | 시간 미선택 | 시간 선택 요청 |
| RES-E06 | 과거 날짜 선택 | 예약 불가 안내 |
| RES-E07 | 영업시간 외 예약 | 운영 정책에 따라 차단 또는 별도 안내 |
| RES-E08 | 휴무일 예약 | 예약 불가 안내 |
| RES-E09 | 임시 휴무일 예약 | 예약 불가 안내 |
| RES-E10 | 예약 가능한 시간 없음 | 다른 날짜 선택 안내 |
| RES-E11 | 입력값 변조 | 서버 측 검증 및 요청 거부 |
| RES-E12 | 존재하지 않는 정비 항목 | 서비스 재선택 안내 |
| RES-E13 | 비활성화된 정비 항목 | 예약 불가 안내 |
| RES-E14 | 다른 회원 소유 차량 선택 | 접근 차단 |

## 7.4 Reservation Conflict Exceptions

| ID | Exception | Expected Behavior |
|---|---|---|
| RES-E15 | 동일 고객의 동일 시간 중복 예약 | 중복 여부 검증 |
| RES-E16 | 동일 차량의 시간 중복 예약 | 중복 여부 검증 |
| RES-E17 | 여러 고객의 동시 예약 요청 | 서버에서 예약 가능 여부 검증 |
| RES-E18 | 예약 화면 진입 후 가능 시간 변경 | 최종 제출 시 재검증 |
| RES-E19 | 관리자에 의한 예약 가능 시간 변경 | 최신 정책 기준으로 검증 |
| RES-E20 | 전화 예약과 온라인 예약 충돌 | 통합 예약 관리 정책 필요 |
| RES-E21 | 예약 처리 중 관리자 상태 변경 | 데이터 정합성 검증 |
| RES-E22 | 예약 요청 중복 전송 | 중복 생성 방지 |

### Reservation Concurrency Principle

예약 가능 여부는 화면에 표시된 정보만으로 확정하지 않는다.

서버는 예약 저장 직전에 최신 예약 현황과 운영 정책을 확인해야 한다.

동시 요청 상황에서도 예약 정책을 위반하는 데이터가 생성되지 않도록 해야 한다.

구체적인 동시성 제어 방식은 Sprint 7에서 검증한다.

## 7.5 Network & Server Exceptions

| ID | Exception | Expected Behavior |
|---|---|---|
| RES-E23 | 예약 요청 중 네트워크 연결 끊김 | 처리 결과 확인 안내 |
| RES-E24 | 서버 응답 지연 | 처리 중 상태 표시 |
| RES-E25 | 서버 오류 | 오류 안내 및 재시도 경로 제공 |
| RES-E26 | 요청은 성공했으나 응답 수신 실패 | 예약 목록에서 결과 확인 안내 |
| RES-E27 | 예약 버튼 연속 클릭 | 중복 요청 방지 |
| RES-E28 | 예약 완료 후 새로고침 | 중복 제출 방지 |
| RES-E29 | 예약 진행 중 뒤로 가기 | 입력 상태와 중복 제출 위험 관리 |
| RES-E30 | 예약 진행 중 세션 만료 | 재로그인 후 안전하게 재진행 |
| RES-E31 | 데이터베이스 저장 실패 | 완료 메시지 표시 금지 |

## 7.6 Reservation Submission State

```text
READY
  ↓
SUBMITTING
  ↓
┌───────────────────────────┐
│                           │
SUCCESS                  FAILURE
│                           │
예약 결과 표시          오류 유형 확인
                            ↓
                     재시도 또는 수정
```

네트워크 장애로 결과를 확인할 수 없는 경우 별도의 `UNKNOWN` 상태를 사용한다.

```text
SUBMITTING
    ↓
NETWORK TIMEOUT
    ↓
UNKNOWN
    ↓
예약 목록 확인
    ↓
결과 확인 후 후속 행동
```

### UX Requirements

- 예약 버튼을 누르면 처리 중 상태를 표시한다.
- 중복 클릭으로 여러 예약이 생성되지 않도록 한다.
- 서버 저장이 확인되기 전에는 예약 완료를 표시하지 않는다.
- 결과가 불확실하면 먼저 예약 목록 확인을 안내한다.
- 예약 실패 시 수정 가능한 입력값은 가능한 한 유지한다.

# 8. Flow 05 — Reservation Status & Cancellation

## 8.1 Objective

고객이 본인의 예약 상태를 확인하고 허용된 조건에서 예약을 취소할 수 있도록 한다.

## 8.2 Happy Path

```text
마이페이지
    ↓
내 예약
    ↓
예약 상세
    ↓
예약 상태 확인
    ↓
예약 취소 선택
    ↓
취소 확인
    ↓
서버 검증
    ↓
예약 취소 완료
```

## 8.3 Exception Scenarios

| ID | Exception | Expected Behavior |
|---|---|---|
| CANCEL-E01 | 존재하지 않는 예약 | 오류 안내 |
| CANCEL-E02 | 다른 회원의 예약 접근 | 접근 차단 |
| CANCEL-E03 | 이미 취소된 예약 | 현재 상태 안내 |
| CANCEL-E04 | 이미 완료된 예약 | 취소 불가 안내 |
| CANCEL-E05 | 취소 가능 기한 초과 | 운영 정책에 따른 안내 |
| CANCEL-E06 | 관리자 처리 중 상태 변경 | 최신 상태 기준으로 검증 |
| CANCEL-E07 | 취소 버튼 중복 클릭 | 중복 처리 방지 |
| CANCEL-E08 | 취소 요청 중 네트워크 오류 | 취소 여부 확인 안내 |
| CANCEL-E09 | 취소 요청 중 세션 만료 | 재로그인 필요 |
| CANCEL-E10 | 사용자의 실수로 취소 버튼 선택 | 최종 확인 단계 제공 |
| CANCEL-E11 | 취소 완료 후 뒤로 가기 | 최신 예약 상태 표시 |
| CANCEL-E12 | 취소 처리 중 DB 오류 | 완료 메시지 표시 금지 |

## 8.4 Cancellation Confirmation

예약 취소는 실제 정비소 운영에 영향을 미치는 작업이므로 확인 단계를 제공한다.

### Confirmation Message

**예약을 취소하시겠습니까?**

예약을 취소하면 기존 예약을 다시 이용할 수 없으며, 필요한 경우 새로 예약해야 할 수 있습니다.

`[돌아가기]` `[예약 취소]`

### Cancellation Policy

- 취소 가능 상태를 서버에서 검증한다.
- 취소 요청 시 최신 예약 상태를 확인한다.
- 취소 완료 후 변경된 상태를 표시한다.
- 취소 불가능한 경우 이유를 명확하게 안내한다.
- 취소 정책은 실제 정비소 운영 기준으로 확정한다.

# 11. Cross-Cutting Exception Handling

## 11.1 HTTP Error Handling

| HTTP Status | Meaning | Customer Experience |
|---|---|---|
| 400 | Invalid Request | 입력 또는 요청 내용 확인 안내 |
| 401 | Authentication Required | 로그인 안내 |
| 403 | Forbidden | 접근 권한 없음 안내 |
| 404 | Not Found | 요청한 정보를 찾을 수 없음 |
| 409 | Conflict | 최신 상태 확인 및 재시도 안내 |
| 422 | Validation Failure | 입력값 수정 안내 |
| 429 | Too Many Requests | 잠시 후 재시도 안내 |
| 500 | Internal Server Error | 일시적인 오류 안내 |
| 503 | Service Unavailable | 서비스 이용 불가 안내 |

※ 실제 HTTP 응답 코드는 기존 Controller와 예외 처리 정책에 맞춰 확정한다. HTML 화면 요청에서는 인증 인터셉터에 의한 로그인 리다이렉트가 발생할 수 있다.

## 11.2 Common Error Message Guidelines

오류 메시지는 다음 세 가지 정보를 전달해야 한다.

1. 어떤 문제가 발생했는가?
2. 현재 작업이 처리되었는가?
3. 사용자는 다음에 무엇을 해야 하는가?

### Examples

| Situation | Message |
|---|---|
| 입력 누락 | 필수 정보를 입력해 주세요. |
| 로그인 만료 | 로그인 시간이 만료되었습니다. 다시 로그인해 주세요. |
| 예약 시간 충돌 | 선택한 시간에 예약할 수 없습니다. 다른 시간을 선택해 주세요. |
| 접근 권한 없음 | 해당 정보를 확인할 권한이 없습니다. |
| 서버 오류 | 일시적인 오류가 발생했습니다. 잠시 후 다시 시도해 주세요. |
| 결과 불확실 | 요청 결과를 확인하지 못했습니다. 예약 내역을 먼저 확인해 주세요. |

## 11.3 Error Display Policy

| Error Type | Display Method |
|---|---|
| 필드 입력 오류 | 해당 필드 주변 |
| 일반적인 작업 실패 | 화면 내 알림 영역 |
| 중요한 상태 변경 확인 | 확인 대화상자 |
| 인증 만료 | 로그인 안내 |
| 페이지 접근 실패 | 오류 페이지 |
| 데이터 없음 | Empty State |
| 일시적인 데이터 조회 실패 | 해당 영역 오류 메시지 |

# 12. Real-World Operational Exceptions

## 12.1 Business Hours

- 정기 휴무일
- 임시 휴무일
- 영업시간 변경
- 특정 시간대 예약 중단
- 예약 접수 마감
- 당일 예약 제한

이러한 조건은 단순히 화면에 표시하는 것뿐 아니라 실제 예약 처리 정책과 일치해야 한다.

## 12.2 Reservation Capacity

실제 정비소의 작업 가능 인원과 정비 공간을 고려해야 한다.

검토할 사항은 다음과 같다.

- 동일 시간대 예약 가능 건수
- 정비 항목별 예상 소요 시간
- 정비 작업 간 시간 중복
- 관리자에 의한 예약 가능 시간 변경
- 전화 예약과 온라인 예약의 통합 관리

초기에는 단순한 예약 정책을 적용하되, 실제 정비소 운영 방식과 충돌하지 않도록 해야 한다.

## 12.3 Unexpected Shop Events

| Scenario | Required Response |
|---|---|
| 정비소 임시 휴무 | 공지 및 신규 예약 제한 |
| 정비사 부재 | 예약 가능 시간 조정 |
| 장비 고장 | 관련 서비스 예약 제한 |
| 기존 예약 처리 지연 | 고객 안내 및 관리자 조정 |
| 예약된 정비 서비스 제공 불가 | 관리자 확인 및 고객 연락 |
| 전화 예약과 온라인 예약 충돌 | 관리자 확인 및 예약 조정 |
| 정비소 운영 정보 변경 | 홈페이지 및 예약 정책 동기화 |

고객에게 이미 확정된 예약이 영향을 받는 경우 단순한 시스템 상태 변경만으로 처리를 완료하지 않는다.

실제 고객 안내 및 조정 절차가 필요하다.

# 13. Security & Privacy Exceptions

## 13.1 Authorization

- 다른 회원의 차량 조회 차단
- 다른 회원의 예약 조회 차단
- 다른 회원의 차량 수정 차단
- 다른 회원의 예약 취소 차단
- 관리자 경로 접근 제한
- 세션 내 유효하지 않은 회원 ID 처리

- 서버 측 입력 검증
- 허용되지 않은 HTML 및 스크립트 처리
- URL 파라미터 변조 검증
- CSRF 보호 정책 적용
- 민감정보의 로그 노출 방지
- 안전한 리다이렉트 경로 검증

## 13.3 Information Disclosure

권한이 없는 사용자는 다른 고객의 개인정보를 확인할 수 없어야 한다.

필요한 경우 리소스 존재 여부 자체가 노출되지 않도록 오류 응답 정책을 검토한다.

# 15. Exception Priority Matrix

예외 상황은 발생 가능성과 영향도를 고려하여 우선순위를 구분한다.

| Priority | Description | Examples |
|---|---|---|
| P0 | 데이터 손상·보안·중복 처리 위험 | 타인 정보 접근, 중복 예약, 잘못된 예약 확정 |
| P1 | 주요 사용자 작업 중단 | 로그인 실패, 예약 실패, 차량 등록 실패 |

# 19. Conclusion

GarageCare의 고객용 웹사이트는 정상적인 예약 흐름뿐 아니라 실제 사용 과정에서 발생할 수 있는 다양한 예외 상황을 고려하여 설계한다.

특히 인증 및 권한 문제, 차량 데이터 정합성, 예약 중복, 동시 요청, 네트워크 장애 및 정비소 운영 정책을 중요한 검증 대상으로 설정한다.

고객이 실수하거나 시스템 장애가 발생하더라도 현재 상태를 이해하고 다음 행동을 결정할 수 있도록 명확한 안내와 복구 경로를 제공한다.

Sprint 6에서는 고객용 화면의 기본 예외 처리와 사용자 경험을 완성하고, Sprint 7에서는 실제 운영 환경에서 예약 처리의 안정성과 데이터 정합성을 검증한다.

이를 통해 GarageCare가 단순히 정상 상황에서 동작하는 서비스가 아니라, 실제 고객이 안심하고 이용할 수 있는 자동차 관리 서비스로 발전할 수 있는 기반을 마련한다.
